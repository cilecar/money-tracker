# Чеки и цены: скан фискального QR, история цен товаров

Дата: 2026-11-05. Статус: дизайн согласован, ждёт ревью спецификации.

## Цель

Сканировать QR сербского фискального чека, сохранять все его позиции и по ним показывать историю цены
товара и сравнение цен между сетями магазинов.

Критерии успеха:

- Скан чека в одно касание; чек привязывается к уже существующему расходу (в том числе к ожидающему
  захвату из Google Wallet) или создаёт новый — без дублей.
- По каждому товару виден график цены за единицу (за кг для весовых, за штуку для штучных),
  отдельной линией на каждую сеть, и сводка «последняя / мин / макс» по магазинам.
- Работает без сети в момент скана: привязка к расходу сразу, позиции догружаются позже.
- Вся система выключается одним тумблером в настройках (по умолчанию выключена).

Решения пользователя:

- Чек ищет существующий расход и прикрепляется к нему; если не нашёлся — создаётся новый расход.
- Позиции чека **не** получают категорий: категория расхода по-прежнему одна и выбирается по магазину.
- Внутри сети товары склеиваются автоматически, между сетями — только вручную (с подсказками).
- Весовые товары: в чеке видно, сколько вышло (вес и сумма), а графики и сравнения строятся по цене за кг.
- Храним конкретную точку магазина, на графиках группируем по сети.
- Графики и аналитика — в отдельной пятой вкладке «Цены» нижней панели.
- Сканер — Google Code Scanner; дополнительно приём ссылки через «Поделиться».

Не входит в v1: категории позиций, возвраты (рефундација) и прочие нефискальные типы чеков, выбор счёта
по способу оплаты из чека, пересчёт фасовки («SOS 400G» → цена за кг), атрибуция скидок к товарам,
пересчёт цен в валюту отображения, чеки других стран, изменения CSV-экспорта.

## Источник данных (проверено на реальном чеке Lidl, 2026-11-05)

QR содержит ссылку `https://suf.purs.gov.rs/v/?vl=<base64>`.

### Локальный разбор `vl` (без сети)

`vl` — URL-encoded base64 бинарной структуры. Проверенные смещения:

| байты | поле | пример |
|---|---|---|
| 0 | версия | `3` |
| 1–8 | `requestedBy` (ASCII) | `WYBQ8YRF` |
| 9–16 | `signedBy` (ASCII) | `WYBQ8YRF` |
| 17–20 | `transactionTypeCounter`, uint32 LE | `344079` |
| 21–24 | `totalCounter`, uint32 LE | `360050` |
| 25–32 | сумма, uint64 LE, в 1/10000 динара | `11979600` → 1197.96 |
| 33–40 | время ПФР, uint64 **BE**, мс эпохи UTC | `2026-11-05T14:28:04.875Z` |
| 41 | `invoiceType` (0 — промет) | `0` |
| 42 | `transactionType` (0 — продажа, 1 — рефундација) | `0` |

Номер чека = `requestedBy-signedBy-totalCounter` (`WYBQ8YRF-WYBQ8YRF-360050`). Принимаются только
`version == 3`, `invoiceType == 0`, `transactionType == 0`; остальное — понятная ошибка. Хост ссылки
обязан быть `suf.purs.gov.rs`.

### Загрузка из сети (3 запроса, один OkHttp-клиент с CookieJar)

1. `GET <ссылка>` с `Accept: application/json` → шапка:
   `invoiceRequest.{taxId, businessName, locationName, address, city, administrativeUnit, payments}`,
   `invoiceResult.{totalAmount, invoiceNumber, sdcTime}`, `journal` (полный текст чека), `isValid`.
2. `GET <ссылка>` (HTML) → из скрипта страницы `viewModel.Token('<uuid>')`; сервер ставит сессионную cookie,
   без которой следующий запрос отвечает `{"success":false}`.
3. `POST https://suf.purs.gov.rs/specifications`, форма `invoiceNumber=…&token=…` →
   `{"success":true,"items":[{gtin,name,quantity,total,unitPrice,label,labelRate,taxBaseAmount,vatAmount}]}`.
   У весовых позиций `quantity` — вес, `unitPrice` — цена за кг.

Запасной путь: если шаг 2 или 3 не удался, позиции разбираются из `journal` (блок между `Артикли` и
`Укупан износ:`; строка названия `Name/UNIT/CODE (Л)`, следующая строка `цена кол. сумма` в формате
`1.197,96`). Если не удалось и это — чек получает статус ошибки, но сумма, время и привязка остаются.

`locationName` имеет вид `1056845-Prodavnica br. 0123`: код точки — часть до первого `-`
(если дефиса нет — вся строка).

### `product` — продукт для графиков

| колонка | тип | примечание |
|---|---|---|
| `id` | PK | |
| `name` | TEXT NOT NULL | при создании = имя артикула, переименовывается |
| `unit` | TEXT NOT NULL | совпадает с единицей всех его артикулов |

Инварианты:

- У каждого артикула всегда есть продукт: новый артикул создаёт свой продукт.
- **Связать** артикул(ы) продукта B с продуктом A = перенести артикулы B в A и удалить B. Разрешено только
  при одинаковой `unit`.
- **Отвязать** артикул = создать для него новый продукт с его именем (нельзя, если артикул в продукте один).
- Удаление чека → удаляются его позиции, затем артикулы без позиций, затем продукты без артикулов.
- Удаление расхода → `receipt.expense_id = NULL`; чек и цены остаются.

### Разбор названия позиции

`ItemNameParser` (чистый `:domain`):

- Формат Lidl `Name/UNIT/CODE`: последний сегмент — цифры, предпоследний — единица (`KG` → `KG`,
  `KOM` → `PCS`, `L`/`LIT` → `L`). → `code = CODE`, `name = Name`.
- Иначе: `code = normalize(raw)` (нижний регистр, схлопнутые пробелы, без хвостового `(Л)`), `name = raw`,
  единица — `KG`, если в названии есть отдельный токен `KG`/`/KG`, иначе `PCS`.
- Новые форматы других сетей добавляются по образцу `GoogleWalletParser` с тестами на реальных образцах.

## 2. Скан и привязка к расходу

### Точки входа

- FAB «Сканировать чек» на вкладке «Цены».
- Чип «Чек» в форме расхода (в строке с датой, временем и «Разделить»). Скан из чипа прикрепляет чек к этому
  расходу без поиска кандидатов. Если чек уже есть — чип «Чек ✓» открывает лист чека. Для несохранённого
  расхода чек привязывается при сохранении.
- Intent `ACTION_SEND` (`text/plain`), содержащий ссылку `https://suf.purs.gov.rs/v/?vl=…`.

Сканер: `com.google.android.gms:play-services-code-scanner`, формат `FORMAT_QR_CODE`; разрешение на камеру
не требуется.

### Поток

1. Разбор ссылки и `vl` (`FiscalLinkParser`). Ошибка → «Это не фискальный чек Сербии».
2. Чек с таким номером уже есть → «Чек уже добавлен», открывается лист этого чека.
3. Сохранение `receipt` со статусом `PENDING`, затем попытка загрузки (таймаут ~5 с, индикатор).
   Успех → `LOADED`, известны магазин и позиции. Неудача → остаётся `PENDING`, ставится фоновая догрузка.
4. Поиск кандидатов (`FindReceiptCandidatesUseCase`):
   - расходы, у которых `amount` в RSD равен сумме чека до пары, `local_date` совпадает с днём чека
     (в часовом поясе пользователя), и к которым не прикреплён чек;
   - ожидающие захваты (`CaptureStatus.PENDING`) с той же суммой в RSD и в тот же день;
   - сортировка по близости времени к времени чека.
5. Показ:
   - один кандидат → лист «Нашёлся расход: сумма · категория · время (источник)» с кнопками
     [Прикрепить] [Создать новый] [Выбрать другой];
   - несколько → список кандидатов и «Создать новый»;
   - ни одного → сразу форма нового расхода;
   - «Выбрать другой» → все расходы этого дня без чека, любой суммы.
6. Новый расход открывается в обычной форме, уже заполненной: сумма и RSD из чека, дата и время чека,
   комментарий — отображаемое имя сети (если чек загружен), категория — `chain.default_category_id`
   (если есть), счёт по умолчанию. После сохранения чек прикрепляется, а категория сохранённого расхода
   записывается в `chain.default_category_id`.
7. Ожидающий захват открывается в существующем редакторе захвата (`saveEdited`); после сохранения чек
   прикрепляется к получившемуся расходу.

Прикрепление не меняет расход (сумма, категория, счёт остаются). Открепление — из листа чека; чек попадает
в «Чеки без расхода».

Ограничение v1: если уведомление Wallet придёт уже после скана (обычно оно приходит раньше), захват не
сопоставляется с расходом из чека автоматически — возможный дубль пользователь отклоняет вручную.

### Фоновая догрузка

`ReceiptSyncWorker` (Hilt-worker, `NetworkType.CONNECTED`, экспоненциальный backoff через существующий
`WorkerRetry`) загружает все `PENDING`-чеки. `isValid == false` или неразбираемый ответ → `FAILED` с
причиной. Ручное «Повторить» снова ставит `PENDING` и запускает воркер.

После загрузки, если `total_amount` шапки не совпадает с суммой из `vl` — побеждает шапка, расход не
меняется.

## 3. Экраны

### Вкладка «Цены» (пятая, видна только при включённом тумблере)

- Поиск по имени продукта.
- Баннер (если есть): «N ожидают загрузки · M без расхода» → экран «Чеки» с нужным фильтром.
- Список продуктов по дате последней покупки: имя; последняя цена за единицу (`/кг`, `/шт`, `/л`), сеть,
  дата; стрелка изменения к предыдущей цене в той же сети (`↑ +5%`).
- Действия в шапке: «Магазины», «Чеки». FAB «Сканировать чек».

### Карточка продукта

- Имя (переименование), единица.
- График (vico): X — дата, Y — цена за единицу, по линии на сеть, вся история, горизонтальная прокрутка.
- По магазинам: сеть → последняя / мин / макс цена, дата последней покупки; раскрываются точки.
- История покупок: дата, точка, количество, цена за единицу, сумма → открывает расход (или чек без расхода).
- Артикулы продукта: `сеть · исходное название` [Отвязать].
- «Связать с товаром из другой сети» → поиск по продуктам с той же единицей, сверху подсказки —
  похожие названия (общие токены после нормализации) из других сетей.

### Лист чека

Магазин (сеть, точка, адрес), время, позиции (`Pileći file · 0,534 кг × 779,99 = 416,51`), скидки отдельно,
итог; статус, если не загружен. Кнопки: [Открыть на сайте налоговой] [Открепить] / [Привязать] [Удалить чек].
Нажатие на позицию открывает карточку продукта.

### «Магазины»

Список сетей: отображаемое имя (редактирование короткого имени), официальное имя, категория по умолчанию
(выбор), число чеков. Раскрываются точки с адресом и числом чеков.

### «Чеки»

Все чеки по дате, фильтр «все / ожидают / ошибка / без расхода»; «Повторить» для ошибок, «Привязать» для
чеков без расхода (поток из раздела 2 начиная с шага 4).

### Настройки

Тумблер «Чеки и цены» (`AppSettings.receiptsEnabled`, по умолчанию `false`, DataStore). Выключен — нет
вкладки и чипа, воркер не ставится; данные не удаляются. Ссылка из «Поделиться» при выключенном тумблере →
диалог «Функция выключена — включить?».

## 4. Бэкап

`BackupDto.VERSION` 3 → 4. Новые необязательные списки (`chains`, `stores`, `receipts`, `receiptItems`,
`articles`, `products`) с пустыми значениями по умолчанию; `SettingsDto.receiptsEnabled` с `false` по
умолчанию. Бэкапы v3 импортируются без изменений. CSV не меняется.

## 5. Ошибки и крайние случаи

| ситуация | поведение |
|---|---|
| ссылка не `suf.purs.gov.rs` или `vl` не разбирается | сообщение, ничего не сохраняется |
| возврат, аванс, копия, обучение | «Этот тип чека пока не поддерживается», ничего не сохраняется |
| повторный скан | «Чек уже добавлен», открывается чек (UNIQUE `invoice_number`) |
| нет сети / 5xx / таймаут | `PENDING`, фоновая догрузка |
| `isValid == false` | `FAILED` с причиной, ручной повтор |
| `/specifications` не отдал позиции | разбор `journal`; если и он не удался — `FAILED` |
| позиция с отрицательной суммой или количеством | хранится как скидка, без артикула, не попадает в цены |
| связывание продуктов с разной единицей | запрещено, объяснение в UI |
| у расхода уже есть чек | в кандидаты не попадает; из чипа — сначала открепить |

Запросы уходят только на `suf.purs.gov.rs`.

## 6. Тестирование

`:domain` (JUnit):

- `FiscalLinkParser`: реальная ссылка Lidl → номер, сумма 1197.96, время; чужой хост, битый base64,
  возврат, неизвестная версия.
- `ItemNameParser`: формат Lidl (KG и KOM), запасной вариант, нормализация.
- `JournalParser`: текст реального чека → 4 позиции с ценами; многострочные названия.
- `FindReceiptCandidatesUseCase`: сумма, день, часовой пояс, ожидающие захваты, исключение уже прикреплённых,
  сортировка.
- Серии цен: за единицу, по сетям, мин/макс, без скидок; стрелка изменения.
- Связывание и отвязывание продуктов, запрет разных единиц, очистка сирот.

`:app` (Robolectric):

- Миграция 5 → 6.
- DAO и репозитории: идемпотентная вставка по номеру чека, `SET NULL` при удалении расхода, каскады и
  очистка сирот, слияние продуктов.
- Клиент SUF на сохранённых ответах реального чека (JSON шапки, HTML с токеном, JSON позиций):
  успех, `success:false` → запасной разбор, `isValid:false`.
- Бэкап v4 туда и обратно; импорт v3.

На телефоне: реальный скан, совпадение с захватом Wallet, офлайн-скан с последующей догрузкой, «Поделиться».
